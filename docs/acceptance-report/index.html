How to run it

These are the README's instructions, and each path below was run exactly like this during the test.

With Docker (one command)

git clone https://github.com/viethq00/simple-invoice.git
cd simple-invoice
docker compose up --build

Open http://localhost:8080 and sign in with admin@simpleinvoice.test / Password123!. No .env is needed: the secrets are generated on first start. docker-compose up --build works too.

ServiceAddress
Web apphttp://localhost:8080
APIhttp://localhost:4000
Swagger UIhttp://localhost:4000/api/docs
PostgreSQLlocalhost:5433

docker compose down -v stops it and deletes the data.

Without Docker

Needs Node.js 24 and PostgreSQL 14 or newer.

npm run setup          # .env with random secrets + installs
# create the DB user with POSTGRES_PASSWORD from .env:
#   CREATE USER simpleinvoice WITH PASSWORD '...';
#   CREATE DATABASE simpleinvoice OWNER simpleinvoice;
npm run seed           # migrations + seed data
npm run dev:backend    # API on :4000
npm run dev:frontend   # web app on :5173

Postgres in Docker instead: npm run dev:db and set POSTGRES_PORT=5433 in .env.

Seed and tests

npm run seed                              # local
docker compose exec backend npm run seed  # Docker
npm test           # unit + component tests
npm run test:e2e   # API tests on real Postgres
npm run verify     # lint, types, all tests, builds
npm run diagrams   # regenerate docs/diagrams (needs Docker)

Operations, secrets and failure cases

Seed inside the container

  • docker compose exec backend npm run seed is idempotent

Secrets

  • generated 64-char secrets, read-only in the API container
  • database container has no JWT or seed variables
  • token signed with a guessable secret is rejected (401)

Logs

  • logs contain no passwords, tokens or secrets (943 lines checked)

Restart persistence

  • after docker compose restart: same 53 invoices, existing session still valid
  • after docker compose down + up: data and secrets kept (53 invoices)

Database outage

  • GET /health answers 503 while the database is down
  • authenticated request answers 500, not 401, during the outage (users are not signed out)
  • recovers on its own once the database is back

Legacy docker-compose command

  • docker-compose up -d --build (standalone binary) brings the stack up with the data intact

.env overrides

  • FRONTEND_PORT from .env moves the web app to :8081
  • JWT_SECRET from .env is the one the API uses
  • SEED_USER_PASSWORD from .env sets the demo login
  • without .env again: back on the defaults with freshly generated secrets

Login rate limiting (runs last: it blocks this IP for a minute)

  • after 10 failed logins a minute the API answers 429 with Retry-After

Diagrams for every pull request

Mermaid diagrams generated from the code. GitHub renders them in the repository, and each pull request gets one comment that shows the diagrams it changes.

What gets generated

npm run diagrams writes four files to docs/diagrams, each read from the code, not drawn by hand:

  • API spec: every endpoint with its inputs and responses, and the request and response schemas, from the OpenAPI document Swagger serves.
  • Architecture: the containers from docker-compose.yml and the Dockerfiles, the Nest modules, every provider and what it injects, and the web app's routes.
  • Sequence diagrams: one per endpoint, traced through the TypeScript source from the guards and pipes down to the database, with every branch that ends in an HTTP error.
  • Data dictionary: an ER diagram and every table, column, constraint and index, read from PostgreSQL's catalog after the migrations run.

What happens on a pull request

  1. The Diagrams workflow regenerates the four files from the pull request's code.
  2. It compares them, section by section, with the base branch and keeps one comment up to date: each changed section is rendered, with its source diff folded underneath.
  3. It fails the job if the committed docs/diagrams differs from what the code produces, so the diagrams can't drift.

Checks

  • All 16 diagrams parse and render with Mermaid 10 and with Mermaid 11
  • Byte-identical output on a second run with different ports, time zone, locale and NODE_ENV
  • 40 unit tests for the generator, inside the 295 backend unit tests
  • A simulated pull request in a scratch copy of the repository, against a stand-in for the GitHub API: all 6 cases below behave as intended
  • actionlint passes on both workflows, and the pinned action versions exist
  • npm run verify passes; the generator is not part of the production build or the Docker image
  • A full run takes about 6 seconds, including a throwaway PostgreSQL in Docker
